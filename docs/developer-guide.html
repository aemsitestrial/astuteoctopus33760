Developer Onboarding

AEM Edge Delivery Services & Adobe Target (Form-Based)

A practical guide for developers new to this project: how the site is built on Edge Delivery Services, how blocks and sections work, and how client-side personalization is wired through Adobe Target using JSON (form-based) offers.

1. What this is

This project is an Adobe Edge Delivery Services (EDS) site (also called Franklin / Helix / "aem.live"). Content is authored as documents or in the Universal Editor, served as plain HTML, then progressively enhanced in the browser by JavaScript "blocks". On top of that, Adobe Target personalizes content client-side using JSON offers applied to stable DOM anchors.

By the end of this guide you should be able to: read the load sequence, build or modify a block, understand Intent Sections, and author + wire a Target experience without breaking Core Web Vitals.

PrerequisitesComfortable with modern vanilla JavaScript (ES modules), the DOM API, and CSS. No framework knowledge needed — EDS is intentionally framework-free.

2. EDS mental model

EDS optimizes for speed and simplicity. Keep these principles in mind:

  • Content is HTML first. A page is delivered as semantic HTML (from a document or the Universal Editor). JavaScript only enhances it — the page is readable and crawlable before any JS runs.
  • Blocks are the unit of interactivity. A block is a folder under /blocks/<name>/ with a <name>.js and <name>.css. The loader finds them by the block's first CSS class.
  • Progressive enhancement. Each block's decorate() function rearranges the delivered markup into its final structure.
  • Performance is a feature. Work is split across three phases (Eager / Lazy / Delayed) so the largest content paints fast and nothing blocks it.
Author (doc / Universal Editor) │ published as plain HTML ▼ Browser loads page → scripts.js runs → decorateMain() finds blocks │ │ each block's decorate() enhances it ▼ ▼ Semantic HTML visible immediately Fully rendered, interactive UI

3. Repo layout

The parts you will touch most:

  <name>.css         block-scoped styles
  _<name>.json       Universal Editor model + definition + filters (xwalk)
/models/
  _component-definition.json   groups (Default Content / Sections / Blocks)
  _component-models.json       aggregates block models
  _component-filters.json      allowed nesting
  _section.json                the default Section
  _intent-section.json         a personalization-friendly Section (has an id field)
/scripts/
  aem.js             EDS boilerplate (loader, decorateSections, createOptimizedPicture…)
  scripts.js         page lifecycle: loadEager / loadLazy / loadDelayed
  target.js          Adobe Target integration (form-based JSON offers)
/styles/             global + lazy styles
/config.json         environment config sheet (endpoints, etc.)
/docs/               guides (you are reading one)
Build stepThe root component-*.json files are generated from the models/_*.json and each block's _<name>.json by npm run build:json. Edit the underscore-prefixed sources, then rebuild — never hand-edit the generated files.

4. The ELD sequence (Eager / Lazy / Delayed)

The whole page lifecycle lives in scripts/scripts.js → loadPage(). Understanding it is essential, because getting phasing wrong is the most common way to hurt performance.

PhaseFunctionWhat belongs here
EagerloadEagerEverything needed for the Largest Contentful Paint: decorate main, load the first (above-the-fold) section, configure Target's SDK. Keep this lean.
LazyloadLazyThe rest of the sections, header, footer, fonts, lazy styles. Runs right after the page is interactive.
DelayedloadDelayedAnything non-essential (analytics, third-party widgets), deferred ~3s so it never competes with the user experience.
Golden ruleNever block first paint on a network round-trip in the eager phase. In this project, loadEager awaits only alloy configuration (alloyLoadedPromise), not the Target decision response. The decision request is fired in parallel and applied asynchronously as blocks decorate.

5. Block anatomy

A block's JS exports a default decorate(block). The loader (in aem.js) resolves the folder and files from the block's first CSS class, so the folder name must equal the block name.

// blocks/example/example.js
export default function decorate(block) {
  // `block` is the <div class="example block"> element.
  // Its children are the authored rows/cells. Read them, then
  // rebuild into the final structure.
  const rows = [...block.children];
  // ...transform...
  block.textContent = '';        // clear
  block.append(/* new structure */);
}
Versioning tipTo ship a new variant without breaking pages that use the old one, create a sibling block folder (e.g. hero-v3), not a nested hero/v3 — the loader only resolves blocks/<name>/<name>.js.

Defensive rendering

Author content is untrusted input. Follow the patterns used across this repo:

  • Set text with textContent, never innerHTML, for authored strings.
  • Validate any URL before writing it to href/src (see isSafeUrl): block javascript:, data:, vbscript:, and protocol-relative (//…) URLs.
  • Null-check every DOM read — assume any row/field may be missing.
  • Reserve layout (min-height, aspect ratio) so async images don't cause CLS.

6. Authoring & models (Universal Editor)

Each block ships a _<name>.json with three parts consumed by the Universal Editor:

KeyPurpose
definitionsRegisters the component (title, id, resource type, template).
modelsThe authoring dialog: the fields an author fills in (text, richtext, reference, aem-content, select…).
filtersWhat can be nested inside (e.g. which blocks a section allows).

Field names in the model become the authored data the block reads. Keeping them meaningful (e.g. title, primaryCtaLink) pays off later — Target offers reference the same names.

Lint gateThe xwalk/max-cells rule caps a block's authoring fields (grouped) at 4 by default. Group related fields with a shared prefix (e.g. cta_link, cta_text) or add a per-model override in .eslintrc.js as the project already does for a few blocks.

7. Worked example: the hero-v3 block

hero-v3 is a clean, inline-authored hero: a full-bleed background image, title, optional subtitle, up to two positional CTAs, and six locked layout variants. It's a good reference for the patterns above.

Data flow

Authored rows (image, title, subtitle, actions) ▼ readInlineData() → normalized { imageSrc, imageAlt, headingEl/titleText, subtitle, actions[] } ▼ renderHero() → builds .hero-media (picture) + .hero-content (title/subtitle/actions) ▼ resolveLayoutConfig() → applies height / alignment / image-position (locked variant wins)

Post-decoration structure

These class names are the stable anchors Target keys off — do not rename them without updating target.js.

<div class="hero-v3 block hero-height-standard hero-align-center …" data-block-name="hero-v3">
  <div class="hero-media"><picture>…<img …></picture></div>
  <div class="hero-content">
    <h2 class="hero-title">…</h2>
    <p class="hero-subtitle">…</p>
    <div class="hero-actions">
      <a class="hero-action hero-action-primary" href="…">…</a>
      <a class="hero-action hero-action-static-light" href="…">…</a>
    </div>
  </div>
</div>
VariantsSelecting a Variant in the model adds a class (e.g. tall-center-with-action); VARIANT_PRESETS maps it to locked height/alignment/image-position so the layout is fixed regardless of authored data.

8. Intent Sections

A normal Section is a layout container. An Intent Section (models/_intent-section.json) is the same idea plus two things that make it a first-class personalization target:

  • It exposes an authored id field. During decoration this is promoted to a real DOM id attribute (a normalized token like hero-intent), usable as a CSS hook, a #anchor target, and a Target decision scope.
  • Its filter allows only text and hero-v3, keeping it focused.
Why it matters for TargetBecause only the intent-section model has an id field, a top-level section that carries an id attribute is definitionally an Intent Section. The Target integration uses that to expose each one as its own decision scope — see §11.

9. Adobe Target — why form-based (and not VEC)

Adobe Target supports two authoring styles. This project uses only form-based (JSON) offers.

VEC / dom-actionForm-Based / JSON used here
Carries a CSS selector?Yes — captured against one DOM snapshotNo — returns a JSON blob per scope
Survives EDS decoration?Rarely — decoration injects wrappers, so positional selectors breakYes — our code anchors to stable classes/ids
Applied byalloy('applyPropositions')Handlers in scripts/target.js
ImportantVEC / dom-action offers are not processed by this project. Author every experience as a JSON offer against a decision scope. Attempting a VEC activity will silently do nothing.

10. How offers apply

scripts/target.js orchestrates everything. Simplified flow of getAndApplyRenderDecisions():

  1. Collect the decision scopes we can handle: the static FORM_BASED_SCOPES (block/section types) plus one scope per Intent Section id (getSectionScopes()).
  2. Fire a single alloy('sendEvent', …) with renderDecisions: false — we render manually, and this never blocks paint.
  3. Keep only the JSON (json-content-item) offers, keyed by scope.
  4. Pre-hide the text those offers will replace (flicker control, §12).
  5. As each block/section decorates (onDecoratedElement), run the matching handler; on success, reveal that scope with a fade.
  6. A hard timeout reveals everything as a failsafe; proposition reporting is deferred off the critical path.

A handler takes the offer JSON and writes it to stable anchors. Two factories cover most cases:

// block-level fields
hero-v3: blockHandler('hero-v3', HERO_V3_FIELDS)
// repeated items matched by label text
metrics: itemHandler('metrics', '.metrics-item', '.metrics-label', { value: '.metrics-value', … })

11. Scopes & offer shapes

A decision scope is the name you give a location in Target; our code maps it to a handler.

Block-type scope

Scope = block name (e.g. hero-v3). The offer's set carries the model-property field names.

// scope: hero-v3
{ "set": { "title": "Welcome back", "subtitle": "Your plan is ready", "primaryCta": "Resume" } }

Intent Section scope (recommended for section personalization)

Scope = the section's id. The offer only needs blocks — a list of single-key objects naming the blocks inside that section to personalize. Because it's scoped to one section, an identical block elsewhere is untouched.

// scope: hero-intent   (the Intent Section's id)
{
  "blocks": [
    { "hero": {
        "title": "Winter sale — up to 30% off",
        "subtitle": "Fixed rates until spring",
        "primaryCta": "Shop the sale",
        "primaryCtaLink": "/sale",
        "image": "https://s7d1.scene7.com/is/image/acme/winter-hero"
    } }
  ]
}

hero-v3 personalizable fields

Field names match the block model, so an offer reads the way an author thinks and survives copy edits (no fragile text matching):

FieldSets
title alias: headingheadline text
subtitlesubtitle text
primaryCta / secondaryCtaCTA button labels
primaryCtaLink / secondaryCtaLinkCTA href (URL-safety-checked)
imagebackground image src (URL-safety-checked; DM-aware)
Multi-instance matchingFor a scope that matches several block instances, use an items array with a match: { "key": "hero-top" } (a data-target-key authored per instance — preferred), { "item": "…" } (label text, for item collections), or { "instance": 1 } (positional fallback).

12. Flicker control (FOOC)

Because offers apply client-side after decoration, the default copy could flash before personalization (flash of original content). The integration prevents this automatically — no authoring step required.

  • Text-only hide. Only the text a returned offer will replace is hidden (h1–h6, p, li, a, cells…). Never the container — so background images, media and scrims stay fully visible (hiding a whole container dimmed the background, which looked wrong).
  • No CLS. Hiding uses opacity:0, so each text box keeps its size.
  • Fade on reveal. When an offer applies, the text fades in (~300ms) instead of snapping, so the swap reads smoothly. Disabled under prefers-reduced-motion.
  • Failsafe. A 3s timeout reveals everything regardless, so content is never stuck hidden if Target is slow or errors.
  • No offer, no hide. A scope that returns nothing is never hidden — unpersonalized content paints immediately.

13. Images & Dynamic Media

Image handling in hero-v3 depends on the URL:

Image URLRendered how
Same-origin DAM path (/content/dam/…, ./media_…)EDS media pipeline via createOptimizedPicture (responsive <source>s + optimize params)
Dynamic Media / Scene7 (/is/image/…, scene7.com, adobedynamicmedia)Rendered directly at its own origin with a wid-based responsive srcset + sizes=100vw
Any other absolute URLRendered directly, src as-is
Why the distinctioncreateOptimizedPicture keeps only the URL pathname (dropping the host) and appends EDS-pipeline params. For a Dynamic Media URL that means the Scene7 host is lost (→ 404) and the params are meaningless to Scene7. So absolute/DM URLs must bypass the optimizer and render directly — which the block does.

This applies both to images authored inline and to images swapped in by a Target image offer. To use a DM background, author (or offer) the full Scene7 delivery URL, e.g. https://s7d1.scene7.com/is/image/yourtenant/hero-banner.

14. Authoring an experience in Adobe Target

  1. Create a JSON Offer (Offers → Create → JSON Offer). Shape it to match the scope's fields (see §11).
  2. Create an activity (A/B or Experience Targeting) using the Form-Based Experience Composer — not Visual.
  3. Add a location / decision scope. Name it either after a block type (hero-v3) or after an Intent Section id (hero-intent).
  4. Assign the JSON offer to the experience for that scope.
  5. Set audiences/goals and activate. The page requests the scope automatically.

Verifying

  • Load the page with the target metadata flag set.
  • DevTools → Network: the …/ee/v1/interact response should include your scope with a json-content-item schema.
  • Confirm the element updates on load — with a smooth fade, no flash of the original copy.

15. Adding a new form-based experience

  1. Add an entry to FORM_BASED_HANDLERS in scripts/target.js (the scope is requested automatically — it's derived from the handler keys). Use blockHandler or itemHandler so multi-instance support comes for free.
  2. Anchor to something stable — best is a data-target-key or an element id; good is a block class + content match; avoid :nth-child positional paths.
  3. Shape the Target JSON offer's fields to match your field map.
  4. Run npm run lint; add unit coverage for the field mapping if it's non-trivial.
myblock: blockHandler('myblock', {
  heading: '.myblock-title',
  cta: '.myblock-actions a.primary',
  ctaLink: { selector: '.myblock-actions a.primary', attr: 'href' }, // sets an attribute (URL-checked)
}),

16. Pull-request checklist

  • Lint npm run lint passes (JS + CSS).
  • Build If you touched a model, ran npm run build:json and committed the regenerated component-*.json.
  • Perf Nothing new added to the eager path that blocks paint; LCP image stays eager + fetchpriority=high; no CLS.
  • A11y Real headings, focus-visible states, 44px touch targets, prefers-reduced-motion respected, contrast checked.
  • Security Authored strings via textContent; URLs pass isSafeUrl; no secrets in code or config.json.
  • Target New anchors documented; offer field names match the handler; verified on preview with the target flag.
  • Branch Work on a feature branch and open a PR (don't push straight to main for code).
